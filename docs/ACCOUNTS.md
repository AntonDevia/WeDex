# Аккаунты на общем VPS · 0.12.0

Один процесс `wedex-server` обслуживает независимые аккаунты. Для администратора есть отдельное Windows-приложение **WeDex Мастер**. Музыкальные приложения Windows и Android не получают SSH-пароль и административный ключ сервера.

## Подключение

1. Администратор устанавливает или обновляет сервис через `WeDex-Master.exe`, используя SSH. Поддерживаются Debian 12/13 и Ubuntu 22.04/24.04, x86_64, systemd. Другие дистрибутивы пока не поддерживаются установщиком.
2. Пользователь открывает «Настройки → Моё облако», вводит адрес вида `https://music.example.org:8765/` или `IP:8765`, проверяет сервер и сверяет SHA-256 сертификата с администратором. Логин и пароль отправляются только после подтверждения сертификата, по HTTPS с закреплённым сертификатом. При смене сертификата потребуется новое подтверждение.
3. «Создать аккаунт»: логин 3–64 латинских символа, цифры, `_`, `.` или `-`; пароль минимум 10 символов, не более 256 байт. Логин не чувствителен к регистру.
4. На следующем устройстве можно войти с тем же логином/паролем либо использовать одноразовое «Пригласить WeDex». Приглашение действует 10 минут и связывает устройство именно с аккаунтом пригласившего.
5. Список устройств и отзыв доступа находятся в «Моём облаке». Пульт работает в основном плеере через выбор устройства. В настройках облака нет отдельного плеера.

Не передавайте SSH-доступ обычным пользователям. Для входа им нужен адрес сервиса и собственный аккаунт. Пароль администратора Linux не является паролем аккаунта WeDex.

## Изоляция

- `accounts.sqlite3` — глобальные логины, соль и зашифрованный ключ аккаунта, хэши токенов для маршрутизации, привязка приглашений к аккаунту.
- `accounts/<UUID>/personal.sqlite3` — отдельная личная база: устройства, приглашения, команды, сессии прослушивания, зашифрованные подключения, список музыки и журнал синхронизации.
- Повторный вход с сохранёнными данными этой установки и правильным паролем сохраняет ID устройства и меняет его токен, в том числе после отзыва доступа. Старый токен перестаёт работать. Без правильного пароля сохранённый отозванный токен не позволяет восстановить доступ.
- Отдельные WebSocket-каналы, очереди команд и уведомления для каждого аккаунта. Клиент не выбирает UUID аккаунта в сообщении: сервер определяет его по токену.
- Проверка команд и отзыва устройств выполняется внутри личной базы. Чужой ID устройства не позволяет прочитать состояние, отправить команду или отозвать доступ.
- Токены устройств и приглашения в базах представлены SHA-256-хэшами. Ключ синхронизации аккаунта сохраняется в обёртке XChaCha20-Poly1305; ключ обёртки выводится Argon2id (19 МиБ, 2 прохода, 1 поток) из пароля и уникальной соли. Пароль и открытый ключ синхронизации не сохраняются в серверной БД. Сервер видит пароль и ключ во время защищённого входа; это не протокол с нулевым знанием.
- Выход и переход на другой аккаунт используют другую локальную SQLite-базу и отдельные записи ключей сервисов. Старые локальные файлы не удаляются. Прежняя локальная медиатека импортируется только в первый подключённый аккаунт этого устройства.

## Общая инфраструктура

Обнаружение зеркал и поиск публичного каталога Hitmo не принадлежат аккаунтам. Поиск идёт через общий серверный обработчик с ограниченным кэшем: 32 страницы до 1 МиБ, TTL 90 секунд, не более 8 запросов к источнику одновременно. В кэш не попадают ключи Яндекса/Last.fm/SoundCloud, статистика и MP3. При недоступности обработчика приложение пробует прежний прямой поиск. Аудио скачивается и кэшируется на устройствах.

Только ключ администратора из «Мастера» разрешает `/api/update` и `/api/update/status`. Обычные и ранее привязанные устройства больше не могут перезапустить общий сервис обновлением. Доступ устройств к своим приглашениям и отзыву своих устройств не даёт административных прав.

Дорогая проверка пароля вынесена из async-потоков; одновременно выполняются максимум две проверки. Вход, регистрация и привязка ограничены 10 попытками в минуту с IP. Это следует учитывать при массовом подключении из одной сети. Персональная база использует WAL и небольшой SQLite-кэш; Redis для первой многопользовательской версии не требуется.

## Перенос старой установки

Обновление не удаляет `cloud.sqlite3`, сертификат, привязанные устройства и историю. Старое личное пространство остаётся отдельным и не показывается новым пользователям.

На прежнем привязанном устройстве с ключом синхронизации создайте аккаунт в «Моём облаке». Сервер проверит токен существующего устройства и закрепит прежнюю базу за этим логином (`legacy`). Другой пользователь не может присвоить эту базу простой регистрацией. Старые приглашённые устройства сохраняют доступ; новые можно подключить по логину либо приглашению. Если старое устройство не имеет ключа синхронизации, сначала передайте ему приглашение с основного устройства.

SSH-установка и штатное обновление создают резервную копию всех личных баз, глобального реестра и идентичности сервера при остановленной службе. Новые базы не заменяют старую схему. Не откатывайте публичный многопользовательский сервис на старую однопользовательскую версию без отдельной проверки совместимости.

## Границы первой версии

Нет email, восстановления забытого пароля, сброса чужого пароля администратором и панели квот. Регистрация открыта тому, кто имеет сетевой доступ к сервису. Пароль необходимо сохранить. Возможность обслуживать 500 активных пользователей не подтверждена нагрузочным тестом: она зависит от CPU/RAM, количества устройств, запросов и скорости внешних каталогов. Приложение не ретранслирует всем пользователям MP3 через VPS.

Проверки покрывают изоляцию двух аккаунтов по реальным TLS/WebSocket-соединениям, приглашение второго устройства, отсутствие доступа к чужому пульту, статистике, библиотеке и ключам, перезапуск, проверку пароля, перенос прежней базы и резервное копирование.
