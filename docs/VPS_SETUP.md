# Автонастройка VPS · WeDex 0.8

Установщик доступен в Windows: **Настройки → Моё облако → Настроить VPS по SSH**. Linux-сервер встроен в EXE; компиляция, Docker, Python и установка Rust на VPS не нужны. Для работы телефона достаточно Android WeDex 0.6.2 или новее.

## Подключение

1. Арендуйте Linux x86_64 VPS с systemd: Debian 12/13 либо Ubuntu 22.04/24.04. Поддержка другого дистрибутива не предполагается автоматически. Сквозная проверка этой версии выполнена на Debian 12; остальные перечисленные ОС проходят проверку семейства/версии, но отдельные ВМ для них не проверялись.
2. Укажите IP, SSH-порт и логин. Для root достаточно пароля либо пути к закрытому SSH-ключу. Поддерживаются ключи OpenSSH/PEM и зашифрованные ключи с паролем. Для обычного пользователя нужен sudo: без пароля либо с паролем из отдельного поля. При входе по паролю SSH он также используется для sudo, если отдельное поле пустое.
3. Оставьте порт WeDex 8765 либо укажите свободный TCP-порт. Он должен отличаться от SSH-порта. Публичный адрес можно оставить пустым: используется адрес SSH. Это адрес, доступный и ПК, и телефону; внутренний адрес VPS обычно не подходит.
4. Нажмите **Установить или восстановить**. При первом соединении сверьте SHA-256 отпечаток SSH-ключа с консолью/панелью провайдера и подтвердите доверие в приложении. При смене ключа подтверждение потребуется снова. До подтверждения пароль и подпись пользовательского ключа серверу не отправляются.
5. Мастер проверит ОС, архитектуру, systemd, права, место и порт, передаст встроенный бинарник по SSH и сверит SHA-256. Установит службу, проверит локальный TLS, затем HTTPS/WebSocket с ПК и автоматически подключит этот WeDex.
6. В «Моём облаке» нажмите **Пригласить WeDex**, скопируйте приглашение на телефон и вставьте в Android **Настройки → Моё облако**. После привязки пульт находится в обычном плеере и дзене. SSH-пароль на телефон не переносится.

Для существующей исправной установки есть **Подключить уже установленную VPS**. Повторная установка сохраняет базу, TLS-идентичность, владельца и устройства. Тот же ПК использует прежний ключ устройства, если он действителен. При смене публичного адреса или порта существующая конфигурация не перезаписывается: требуется отдельная миграция; автоматическая ротация сертификата в этой версии не реализована.

## Что устанавливается

- `/opt/wedex/releases/<версия>-<sha256>/wedex-server` и атомарная ссылка `/opt/wedex/current`.
- `/etc/wedex/server.json`, маркер установки `/etc/wedex/install.json`.
- `/var/lib/wedex`: SQLite, сертификат, закрытый TLS-ключ и идентичность владельца.
- `wedex.service`: пользователь `wedex`, автозапуск, перезапуск при сбое, ограничения прав и памяти 256 МБ. На портах ниже 1024 даётся только `CAP_NET_BIND_SERVICE`.
- Перед повторной установкой база и конфигурация копируются при остановленной службе в `/var/backups/wedex/<UTC>-<pid>/`. Архивы автоматически не удаляются. Они занимают место на том же VPS и не заменяют внешнюю резервную копию.

Установщик не выполняет обновление ОС и не перезагружает VPS. Чужие каталоги/служба с таким же именем и существующий неуправляемый пользователь `wedex` приводят к отказу, а не перезаписи. SSH, чужие службы и правила firewall не сбрасываются. Если UFW активен, добавляется разрешение только выбранного порта WeDex. Для другого firewall и панели хостинга может потребоваться разрешить порт вручную; публичная проверка покажет, что сервер пока недоступен.

Бинарник доверенный как часть самого Windows-приложения, а не загружаемый VPS из внешнего репозитория. SHA-256 защищает передачу/развёртывание; сетевые обновления с проверкой digest GitHub описаны в [UPDATES.md](UPDATES.md). При сбое обновления выполняется попытка вернуть предыдущий бинарник; резервная копия сохраняется. Автоматического отката произвольных будущих миграций схемы БД нет.

## Хранение доступа

Пароли SSH/sudo и пароль ключа используются только в текущей фоновой операции и очищаются из формы; для них используются обнуляемые буферы. На диск они не сохраняются, в аргументы процесса/журнал не передаются. Запоминаются адреса/логин/путь к файлу ключа и подтверждённый отпечаток. Ключ устройства и право владельца облака хранятся в Windows Credential Manager. На Android — собственный отзываемый ключ устройства в Keystore-хранилище.

HTTPS и WSS проверяют сертификат сервера, полученный через доверенный SSH-канал или приглашение. Проверка TLS не отключается; обязательного домена и внешнего сертификата нет. Служба не выводит приглашения или ключ владельца в journald.

Уже работают пульт и синхронизация новых сессий прослушивания. Telegram-архив, постоянное хранилище Hitmo, единая медиатека и годовые карточки статистики остаются отдельными этапами.

## Сборка и проверки

Для Windows-сборки сначала подготовьте Linux-сервер: `python tools/build_server.py --zig-dir PATH_TO_ZIG`, затем `scripts/package.ps1`. Нужны Rust target `x86_64-unknown-linux-musl` и `cargo-zigbuild`. На Linux с musl-gcc: `python3 tools/build_server.py`. CI собирает статический Linux-бинарник перед Windows-приложением. Обычная сборка исходников без этого файла запускается, но установщик объяснит, что нужен полный дистрибутив.

Автотесты: `cargo test --workspace --locked`. Проверяются TLS для публичного имени, административная CLI, отсутствие приглашений в служебном выводе, отказ неподтверждённому/изменённому SSH-ключу, входные данные и форма без потери фокуса.

На изолированной Debian 12 ВМ проверены первая установка по root-паролю, SSH-ключ + sudo, sudo с паролем, повторная установка и подключение без установки. Проверены автозапуск службы и повторное подключение после перезагрузки ВМ, внешний HTTPS/WSS, сохранность TLS-ключей/владельца/устройств, создание резервной копии и отказ неподтверждённому SSH-ключу. Реальная арендованная VPS и firewall конкретного провайдера без её реквизитов не проверялись.

## Обновление из приложения · 0.8

Новый установщик добавляет systemd-обработчик обновлений. После однократной SSH-установки обновления VPS запускаются с ПК владельца по HTTPS без сохранения SSH-пароля. Серверные релизы имеют отдельную версию. Схема, резервное копирование и ограничения: [UPDATES.md](UPDATES.md).

На изолированной Debian 12 ВМ выполнено сетевое обновление сервера 0.8.1 → 0.8.2 из настоящего релиза GitHub Actions через авторизованный HTTPS-запрос. Проверены автоматический перезапуск, состояние `done`, сохранность базы, сертификата и устройств; повторный запрос возвращает `up_to_date`. На предрелизном стенде также проверен возврат прежнего бинарника при неудачной проверке запуска.
