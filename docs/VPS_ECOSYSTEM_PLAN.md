# План WeDex Cloud: личная VPS, установка из приложения и несколько устройств

Статус: план реализации, 8 ноября 2026 года. Windows 0.7.0 добавляет SSH-мастер установки встроенного Linux-сервера, systemd, TLS по IP и подключение существующей VPS; сценарий проверен на Debian 12 ВМ. Android 0.6.2 подключается по приглашению и управляет ПК через основной плеер. Telegram-архив, мобильная SSH-привязка, подписанные сетевые обновления и полная синхронизация медиатеки ещё не реализованы. Инструкция текущей поставки — [VPS_SETUP.md](VPS_SETUP.md). Следующие разделы описывают целевой сценарий, включая последующие этапы.

## 1. Цель и границы прототипа

Пользователь арендует VPS и подключает её из WeDex на Windows по IP, SSH-порту, логину и паролю либо закрытому SSH-ключу. WeDex проверяет сервер и устанавливает собственную Linux-службу. После установки устройства пользователя получают общую медиатеку, статистику, резервные копии Hitmo-аудио в Telegram и удалённый пульт.

Первый профиль — один владелец VPS с несколькими устройствами. Общий коммерческий сервер для множества независимых пользователей, бесплатные хостинги и семейные аккаунты относятся к следующим версиям. Облачные модули отключаемы; обычное локальное воспроизведение работает самостоятельно.

На сервере снова доступен полноценный WebSocket: короткий периодический опрос не является основным транспортом пульта.

## Локальный этап до аренды VPS

Первый серверный прототип разрабатываем и запускаем на Windows-ПК пользователя. Это тот же `wedex-server` с тем же API и схемой базы, который впоследствии собирается для Linux. Серверная бизнес-логика не должна зависеть от systemd, SSH-установщика или Windows UI.

- Локальный процесс использует отдельную папку данных и свою SQLite, не открывает базу desktop-приложения напрямую.
- Сначала сервер слушает loopback, а два тестовых клиента на одном ПК проверяют регистрацию, команды и статистику.
- Для проверки на втором ПК/телефоне включается режим домашней сети: прослушивание выбранного LAN-интерфейса, доступ только привязанным устройствам и явное разрешение нужного порта в частном профиле Windows Firewall. Автоматический проброс портов роутера не требуется.
- В настройках desktop-клиента появится «Локальный сервер». Приложение сможет запускать и останавливать дочерний серверный процесс и показывать адрес, состояние и приглашение. Первый запуск не требует SSH-пароля.
- Telegram-модуль обращается к Telegram с этого ПК. Если Telegram API с ПК недоступен, архивный сценарий до появления доступного серверного соединения не проходит; успешный локальный пульт не считается успешной проверкой архива.
- До Android-клиента пульт проверяется двумя экземплярами desktop-клиента. Небольшой браузерный диагностический пульт можно использовать для проверки с телефона отдельно; он не заменяет нативный мобильный клиент, не получает root-данные и требует собственного способа подключения с учётом доверия TLS.
- Пока ПК выключен или серверный процесс остановлен, облачные функции недоступны. Без дополнительной сетевой настройки телефон подключается из той же доступной домашней сети; работа через мобильный интернет не входит в локальный этап.

Автоустановку по SSH и systemd проверяем отдельно на локальной Linux-ВМ; WSL2 допустим для первичных проверок, но сетевой и системный сценарий затем проверяется на полноценной ВМ/чистой VPS. Установка дополнительной среды не выполняется как неявная часть проверки текущего проекта.

Переезд на VPS: остановить локальную службу, сделать согласованный экспорт базы, конфигурации и нужных промежуточных файлов, развернуть Linux-релиз, импортировать данные и перепривязать адрес/идентичность устройств через доверенное действие. Токены и TLS-идентичность переносить отдельным защищённым шагом. Два сервера не должны одновременно обрабатывать один Telegram-бот и одни очереди. Для локального Telegram Bot API соблюдать официальную процедуру его миграции.

## 2. Что уже есть в репозитории

- Windows-приложение Rust/egui, отдельный аудиопоток и команды плеера: `src/app.rs`, `src/audio.rs`, `src/glass/mod.rs`.
- Метаданные, настройки и медиатека в SQLite; секреты в Windows Credential Manager: `src/store.rs`.
- Текущая история хранит максимум 500 запусков треков. Она не содержит измеренной длительности прослушивания; прошедшие минуты из неё восстановить нельзя.
- Аудио загружается в ограниченный буфер памяти. Постоянной файловой медиатеки и облачного архива пока нет.
- Android-клиент 0.6.2 использует общий Rust-код, локальный аудиодвижок и основной плеер как пульт ПК. Привязка выполняется приглашением; мобильная SSH-привязка, QR и скачивание архива относятся к следующим этапам.

## 3. Состав серверного комплекта

Основная программа — `wedex-server` на Rust:

- Tokio + Axum: HTTPS API, WebSocket, загрузка и скачивание файлов.
- rustls: TLS прямо в сервере, чтобы начальный запуск работал по IP без обязательного домена.
- SQLite в режиме WAL: один владелец, устройства, каталог файлов, история, агрегаты и состояния синхронизации. Запись через ограниченную очередь, тяжёлые операции вне сетевого потока.
- Встроенные модули: авторизация устройств, пульт, синхронизация, статистика, Telegram-архив и ограниченный файловый кеш.
- systemd: запуск после перезагрузки, перезапуск при сбое и ограниченные журналы.

PostgreSQL и отдельный брокер сообщений для первого личного сервера не требуются. При росте нагрузки слой хранения должен допускать замену базы.

Telegram работает в двух профилях:

1. Стандартный облачный Bot API: требуется токен собственного бота, скачивание ограничено 20 МБ на файл.
2. Полный архив: установщик разворачивает официальный `telegram-bot-api` как дополнительную службу на той же VPS. Нужны токен бота и собственные `api_id`/`api_hash`. Этот профиль снимает ограничение 20 МБ на скачивание и поддерживает загрузки до 2000 МБ в рамках Telegram Bot API.

Интерфейс показывает один сервер WeDex; дополнительный Telegram-процесс устанавливается и обслуживается тем же мастером. Его внутренний порт доступен только локально. Миграция бота между облачным и локальным Bot API выполняется по официальной процедуре, без двух конкурирующих получателей обновлений.

Для облегчённого профиля ориентир — 1 vCPU, 1 ГБ RAM, 15 ГБ диска. Для полного Telegram-профиля предварительно рекомендовать 2 ГБ RAM; возможность стабильной работы на 1 ГБ подтвердить измерениями, а не обещать заранее. Готовые Linux-бинарники загружаются из релиза: сборка Rust и C++ на маленькой VPS не нужна.

## 4. Мастер установки в Windows

В настройках появляется «Моё облако» с действиями «Подключить сервер» и «Установить или восстановить».

Поля: IP/домен, SSH-порт (22 по умолчанию), имя пользователя, пароль или файл SSH-ключа, пароль зашифрованного ключа при необходимости. Поддержать root и пользователя с sudo; интерактивное повышение прав учитывать отдельным состоянием мастера.

Последовательность:

1. Установить SSH-соединение, показать и запомнить отпечаток SSH-ключа сервера при первом доверии. Изменение ключа требует явного повторного доверия.
2. Проверить ОС, архитектуру, права, свободный диск, доступные порты, время и доступ к необходимым релизам/Telegram. Начальная поддержка: Ubuntu 24.04 LTS и Debian 12, Linux x86_64. Остальные сочетания показывать как неподдерживаемые.
3. Найти существующую установку по её manifest и идентификатору. Различать новый сервер, исправную установку, прерванный этап и несовместимую более новую версию.
4. На чистом сервере создать системного пользователя `wedex`, каталоги, конфигурацию, TLS-идентичность и базу. Служба работает без root; привязка к 443 настраивается средствами systemd.
5. Скачать подписанный релиз нужной архитектуры, проверить подпись и хеш до запуска. Публичный ключ проверки поставляется с клиентом.
6. Установить службу, настроить доступ к выбранному порту, сохранив действующий SSH-доступ и чужие правила. Не сбрасывать firewall, SSH-конфигурацию и существующие сервисы. Если 443 занят, предложить другой порт.
7. Подключить Telegram в отдельном шаге: пользователь создаёт бота через BotFather, WeDex проверяет токен и связывает нужный Telegram-чат. Автоматическое создание бота за пользователя не обещается.
8. Создать владельца и ключ первого устройства через уже проверенный SSH-канал.
9. Проверить HTTPS/WebSocket с самого ПК, пробную синхронизацию и, при настроенном архиве, загрузку/скачивание небольшого тестового файла с совпадением контрольной суммы.
10. Показать готовность модулей и оставить сервер в настройках. Если внешний firewall провайдера закрывает порт, показать конкретный порт и инструкцию; без API провайдера клиент не может гарантированно изменить это правило.

Пользователь видит шаги с состояниями, повтором неудачного шага и подробным журналом без секретов. Установка допускает повтор после обрыва SSH. Отмена оставляет понятное состояние, но не удаляет уже существующие данные. Обновление ОС целиком и автоматическая перезагрузка в установку не входят.

Работающий сервер подключается без повторной установки. Локальные проверки не загружают реальные пользовательские секреты на произвольную тестовую VPS.

## 5. Подключение телефона и дополнительных ПК

Два способа:

- Основной: QR-код или приглашение от уже подключённого ПК. Приглашение содержит адрес, идентичность TLS-сервера и одноразовый код с ограниченным сроком действия; root-пароля в нём нет.
- Ручной: IP, SSH-логин, пароль или SSH-ключ, как предложено пользователем. Мобильный клиент по SSH проверяет уже установленный WeDex и через его локальную команду регистрации получает отдельный ключ устройства и TLS-идентичность. Установку и обновление Linux-служб телефон не выполняет.

После первичной привязки телефон использует HTTPS/WSS и свой отзываемый ключ устройства. SSH-пароль нужен для первоначального доступа и не требуется для каждого запуска. Новый телефон не может захватить незарегистрированный сервер через публичный HTTP endpoint: первая регистрация доступна через SSH/локальную CLI.

Для подключения по IP без домена клиент закрепляет публичный ключ TLS-сервера, полученный по SSH или из доверенного приглашения. Проверки TLS не отключаются глобально. Ротация идентичности и восстановление сервера выполняются отдельным подтверждаемым действием. При появлении домена можно добавить публично доверенный сертификат.

## 6. Пульт и воспроизведение

- У каждого устройства есть имя, идентификатор, возможности и статус доступности.
- Плеер показывает место воспроизведения: «Этот компьютер», «Телефон» и другие подключённые устройства.
- Сервер передаёт команды по WebSocket. Запрос содержит `command_id`, целевое устройство, срок действия и ожидаемую версию состояния при необходимости.
- Играющее устройство выполняет существующую команду плеера и возвращает результат. Именно оно подтверждает текущий трек, паузу, позицию, очередь, громкость, shuffle и repeat.
- Для сети использовать отдельные идемпотентные операции `SetPlaying`/`SetPaused`, а не слепое повторение локального переключателя Pause. Дубликаты Next/Previous не выполняются повторно.
- После переподключения передавать актуальный снимок и версии состояния. Просроченные нажатия не проигрывать пачкой.
- Прогресс между снимками рассчитывается на клиенте по позиции, скорости и времени снимка; отправлять каждую секунду запись в БД не нужно.
- Прослушивание учитывается только на устройстве, которое действительно выводит звук. Телефон-пульт не создаёт вторую запись статистики.
- Аудио Яндекса и других подключённых стримингов идёт на играющее устройство напрямую. Ключи этих сервисов по умолчанию остаются на устройствах.

Для передачи воспроизведения с ПК на телефон отдельная операция: подготовить запись на телефоне, дождаться готовности, затем согласованно сменить устройство. Это следующий шаг после обычного дистанционного управления, а не автоматическое свойство WebSocket.

## 7. Постоянный кеш и Telegram-архив Hitmo

Сначала нужен постоянный локальный кеш: содержимое RAM-буфера ещё не является сохранённым аудиофайлом.

Цепочка:

1. WeDex на ПК завершает загрузку Hitmo-аудио во временный файл, проверяет полноту и вычисляет SHA-256.
2. Пользовательская настройка определяет, какие записи архивировать: например, сохранённые треки Hitmo. Не загружать в архив все прослушанные треки без выбранной политики.
3. Клиент проверяет наличие такого содержимого в каталоге и при необходимости загружает файл на свою VPS с возможностью продолжить передачу.
4. Фоновая задача отправляет файл в Telegram. Успешный ответ и метаданные сохраняются в БД до удаления промежуточной копии.
5. Телефон получает каталог и запрашивает файл по внутреннему идентификатору. VPS получает файл из Telegram и отдаёт через HTTPS с поддержкой Range, докачки и контролем доступа.
6. Телефон проверяет контрольную сумму и сохраняет собственную копию. Telegram-ссылки и токен бота в ответах API отсутствуют.

Каталог хранит точную версию записи: remix/live/clean/explicit не объединяются только по названию. Признаки «локально», «загружается», «в облаке», «ошибка» имеют разные состояния; наличие записи в каталоге не означает успешную загрузку аудио.

Резервная копия должна успеть попасть в Telegram до отключения ПК или исчезновения исходника. Если файл существует только на выключенном ПК и ещё не загружен, сервер не может получить его самостоятельно.

Кеш VPS ограничен размером и свободным местом; имеются очереди, повтор с задержкой, предел параллельных передач и резерв диска для БД/ОС. Состояние Telegram Bot API и его локальные файлы учитываются в общем бюджете отдельно от кеша WeDex. Серверный сетевой трафик включает доставку аудио устройствам.

## 8. Статистика и синхронизация

- Новые `listening_sessions` и исходящая очередь на устройствах; текущую короткую историю рекомендаций оставить отдельной.
- Учитывать фактически проигранные интервалы по монотонным часам, без пауз, ожидания сети и скачков позиции при перемотке.
- Каждая сессия имеет глобальный UUID, устройство и возрастающую ревизию. Повторная отправка обновляет запись идемпотентно; старые ревизии не затирают новые.
- При crossfade отдельно определить правило: воспроизведённое время треков может пересекаться, а общие минуты активности пользователя считаются объединением интервалов. Два одновременно играющих устройства также не должны случайно удваивать общие минуты активности.
- UTC хранится вместе с нужными данными часового пояса; границы дня/года определяются выбранным пользовательским поясом.
- Пакетная синхронизация работает после офлайна и перезапуска. Сервер возвращает курсор изменений; клиент не скачивает весь архив при каждом запуске.
- Первые экраны: сегодня, месяц, год; минуты, топ треков и исполнителей, календарь и новые открытия. Жанры показывать только при достоверных метаданных.
- Итоги строить из накопленных данных, не обещать восстановление прошлых лет из 500 старых запусков.
- Зафиксировать правила подсчёта «прослушанного трека» отдельно от суммы секунд и показывать их в справке статистики.

## 9. Обновления, резервные копии и обслуживание

- В Windows: состояние сервера, версия, модули, устройства, занятый диск, очередь архива, ошибки, «Обновить», «Восстановить», «Скачать резервную копию».
- Обновления — подписанные бинарники, проверка совместимости API, корректное завершение задач и миграции схемы. Новую версию проверять healthcheck до завершения обновления.
- Перед миграцией — согласованная резервная копия SQLite и конфигурации. Откат бинарника возможен только при совместимой схеме; иначе восстановление согласованной копии с учётом записей, появившихся после неё.
- Резервные копии БД не должны оставаться единственной копией на том же диске VPS. Поддержать скачивание на ПК и последующий экспорт зашифрованной копии в выбранное хранилище.
- Отзыв устройства закрывает его доступ и соединения; журнал не содержит SSH-паролей, bot token, provider tokens или приватных ключей.
- Удаление серверного ПО и удаление пользовательских данных — отдельные действия. Сторонние службы VPS сохраняются.

## 10. Порядок реализации и критерии готовности

| Этап | Результат | Проверка готовности |
| --- | --- | --- |
| 0. Локальный стенд | Windows-сборка `wedex-server`, отдельная папка данных, loopback и опциональный LAN-режим | Два клиента на одном ПК работают через настоящий API; серверные данные не смешиваются с desktop-базой |
| 1. Контракт и каркас | Общий протокол, `wedex-server`, версия API, SQLite-миграции, HTTPS/WSS и регистрация устройств | Два тестовых клиента получают свои права; перезапуск сохраняет состояние; чужой ключ отклоняется |
| 2. Серверный релиз | Linux x86_64 бинарники, systemd, подписанный manifest, CLI установки/диагностики | Развёртывание на чистых поддерживаемых ОС, работа после reboot, проверка ограниченных ресурсов |
| 3. Мастер Windows | SSH-пароль/ключ, установка, подключение существующего сервера, повтор неудачного этапа | Полный путь из UI без терминала; обрыв сети и повтор не создают вторую установку и не теряют БД |
| 4. Пульт | Подключение двух Windows-клиентов, выбор играющего устройства, управление и очередь | Pause/Next/Seek/Volume исполняются на выбранном устройстве; дубликат не повторяет Next; reconnect восстанавливает снимок |
| 5. Статистика | Новые сессии, офлайн-очередь, синхронизация, первые итоги | Пауза и перемотка не добавляют фиктивные минуты; повтор пакета и телефон-пульт не удваивают статистику |
| 6. Архив Hitmo | Постоянный кеш, каталог, Telegram, докачка и квоты | Передать файл с ПК через Telegram на второй клиент с совпадением SHA-256; исходный сайт и ПК после загрузки недоступны |
| 7. Android-прототип | Общий Rust-протокол/клиент, адаптированная мобильная оболочка, QR и ручная SSH-привязка | Телефон управляет ПК и скачивает архивный трек без прямого обращения телефона к Telegram; мобильный установщик VPS отсутствует |
| 8. Полировка и выпуск | Обновление, восстановление, резервные копии, диагностика и инструкции | Полный сценарий на новом сервере, обновление без потери данных, восстановление из внешней копии |

В этапе 7 сначала сделать вертикальный сценарий пульта, затем локальный аудиоплеер и скачивание. Полный перенос всех экранов desktop-приложения на Android не является условием первого серверного теста. Общие команды, модели и сетевой код выделяются из Windows-зависимой оболочки; готовность Android-сборки проверяется отдельно.

Оценки задержки и вместимости подтверждаются измерениями на выбранной VPS. Для пульта измерять время от команды до подтверждения, для архива — полный цикл файла и поведение при заполнении диска. Нагрузочные проверки проводить с известными размерами сообщений и количеством подключений.

Первый законченный прототип: Windows сама устанавливает облако; второй клиент подключается; пульт управляет ПК; статистика синхронизируется; заранее загруженный Hitmo-трек восстанавливается из Telegram при недоступном исходнике. После этого закрывается мобильный сценарий.

## 11. Изменения структуры проекта

Постепенно выделить Cargo workspace, сохранив запуск существующего desktop-бинарника:

- `crates/wedex-protocol`: сериализуемые сетевые модели и версия протокола, без egui/Windows/аудиодрайверов.
- `crates/wedex-cloud-client`: HTTPS/WSS, доверие серверу, синхронизация, переподключение и приглашения.
- `crates/wedex-server`: Linux-служба и локальная административная CLI.
- `crates/wedex-provision`: SSH-проверки и управление установкой; UI мастера остаётся в desktop-приложении.
- Платформенно независимые модели и учёт прослушивания выделять по мере использования вторым клиентом; Windows tray, keyring backend и текущий UI остаются в соответствующей оболочке.

Новые сетевые команды должны проходить через общий диспетчер действий приложения, не имитировать клики по интерфейсу. Сетевые фоновые задачи не блокируют UI и не владеют напрямую аудиоустройством.
